# تقرير قسم الخادم: الاشتراكات والمعاملات الذرية

## المشكلة المكتشفة

كان مسار `changeSubscription` ينفذ قراءة الاشتراك الحالي ثم يقرر بين الإدراج والترقية خارج معاملة واحدة. وكان `createUserSubscription` ينشئ اشتراكاً نشطاً مباشرة، بينما كان الإلغاء يستخدم تحديثاً منفصلاً. هذا يترك نافذة تنافس يمكن أن تنشئ اشتراكين نشطين للمستخدم نفسه عند وصول طلبين متزامنين.

## الإصلاح المطبق

أضيفت معاملة ذرية موحدة في `server/db.ts` باسم `changeUserSubscriptionAtomically`. تبدأ المعاملة بقفل صف المستخدم عبر تحديث لا-تغييري، ثم تقرأ الاشتراكات النشطة داخل المعاملة، وتمنع الإنشاء إذا كان هناك اشتراك نشط قائم. إذا لم يوجد اشتراك، يتم الإدراج داخل المعاملة نفسها. وإذا وجد اشتراك واحد، تُسجل حركة التغيير ويُحدّث الاشتراك داخل المعاملة نفسها.

أصبح تكرار طلب الخطة نفسها عملية **idempotent** لا تنشئ تاريخاً زائفاً ولا اشتراكاً جديداً. كما أصبح الإلغاء يستخدم `cancelUserSubscription` الذري، وأصبح مسار التحديث العام يرفض إعادة تفعيل اشتراك عند وجود اشتراك نشط آخر. أضيف ترتيب ثابت للاشتراك النشط، ودالة قراءة `getActiveUserSubscriptions` لاستخدام التحقق والاختبارات.

## قرار التعامل مع البيانات القائمة

لا تزال الحالات الثلاث التي اكتُشفت سابقاً لحسابات اختبارية، ولكل منها اشتراكان نشطان، موجودة دون تعديل. السبب أن إلغاء أحدهما يحتاج سياسة أعمال صريحة تحدد الخطة المرجعية أو آلية رد/تسوية. الإصلاح الحالي يمنع تكوين حالات جديدة ويجعل الحسابات السليمة مقاومة للتنافس، بينما تُرحّل تسوية البيانات القديمة إلى مهمة مستقلة بعد اعتماد سياسة الاشتراكات.

## فجوات مؤجلة

تشغيل مجموعة Vitest العامة سابقاً كشف 8 إخفاقات مرتبطة بمسارات HTTP تعيد 404 بدلاً من 400/401/403، وهي ليست ناتجة عن المعاملة الذرية وستُراجع ضمن تدقيق المصادقة وواجهات API. كما يجب لاحقاً إضافة اختبار قاعدة بيانات مخصص للترقية المتزامنة بين خطتين مختلفتين.

**حالة القسم:** اكتمل إصلاح منع الازدواج الجديد بالمعاملة الذرية، ونجحت اختبارات الاشتراكات والبناء. التوقف التالي يكون قبل تدقيق SMS، مع بقاء فجوات HTTP وتسوية الحسابات الاختبارية ضمن قائمة المتابعة.
