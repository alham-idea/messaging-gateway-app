# تقرير القسم الثاني: تدقيق قاعدة البيانات والعلاقات والهجرات

**التاريخ:** 2026-08-23

## نطاق التدقيق

تمت مقارنة `drizzle/schema.ts` و`drizzle/relations.ts` وملفات الهجرة الخمسة مع البنية الفعلية لقاعدة MySQL. أُجريت الاستعلامات بصيغة قراءة فقط باستثناء تطبيق هجرة العلاقات التي تمت مراجعتها مسبقاً. لم يتم إدراج بيانات اختبار أو حذف أو تعديل سجلات أعمال.

## الحالة الفعلية

| المؤشر | النتيجة |
|---|---:|
| جداول التطبيق | 18 جدولاً |
| جدول إدارة الهجرات | `__drizzle_migrations` |
| الهجرات المسجلة بعد الإصلاح | 6 |
| محرك الجداول | InnoDB |
| ترميز الجداول | `utf8mb4_bin` |
| المفاتيح الخارجية قبل الإصلاح | 0 |
| المفاتيح الخارجية بعد الإصلاح | 22 |
| السجلات اليتيمة في أعمدة الربط المفحوصة | 0 |
| مستخدمون لديهم أكثر من اشتراك نشط | 3، وكلها حسابات اختبارية |

تطابقت الجداول الفعلية مع الجداول المعرفة في المخطط، وتطابقت الهجرات المسجلة مع سلسلة Drizzle بعد تسجيل الهجرة الجديدة `0005_wise_xorn`. جميع الجداول تستخدم InnoDB، ولذلك أصبحت القيود المرجعية قابلة للتطبيق على مستوى قاعدة البيانات.

## المشاكل التي عولجت

كان `drizzle/relations.ts` فارغاً عملياً، كما أن أعمدة الربط في `schema.ts` لم تكن تولد مفاتيح خارجية. أضيفت العلاقات الصريحة بين المستخدمين والاشتراكات والخطط والفواتير والمدفوعات والاستردادات والأجهزة والإشعارات وطابور البريد والكوبونات. أضيفت كذلك مراجع Drizzle إلى أعمدة الربط في المخطط، ثم وُلدت الهجرة `drizzle/0005_wise_xorn.sql` وطبقت على قاعدة البيانات باستخدام `ON DELETE NO ACTION` و`ON UPDATE NO ACTION` لتجنب الحذف المتسلسل غير المقصود.

تم التحقق من عدم وجود سجلات يتيمة قبل التطبيق وبعده. كما تم تسجيل بصمة الهجرة في `__drizzle_migrations` والتحقق من أن `pnpm drizzle-kit migrate` لا يعيد تنفيذها.

## الفجوة المتعلقة بالاشتراكات

يوجد ثلاثة مستخدمين اختباريين لديهم اشتراكان نشطان في الوقت نفسه، بواقع اشتراكين لكل مستخدم. لم أقم بإلغاء أي اشتراك تلقائياً لأن اختيار الاشتراك الصحيح قرار أعمال، ولأن الحسابات المعنية تبدو بيانات اختبارية وليست حالة فساد مرجعي. هذه الفجوة ستُعالج في قسم الخادم ومنطق الاشتراكات عبر معاملة ذرية وقاعدة واضحة تمنع إنشاء اشتراك نشط ثانٍ أو تحدد سلوك الترقية والتجديد صراحة.

## التحقق البرمجي

نجح `pnpm drizzle-kit check` و`pnpm check`، وتأكدت سلامة الهجرة والمخطط. شغلت مجموعة Vitest العامة؛ نجحت 120 حالة وفشلت 8 حالات في اختبارات أمن وتدفقات تعتمد على مسارات HTTP غير متاحة في سياق الاختبار، إذ أعادت بعض الحالات 404 بدلاً من 400/401/403. لا يبدو أن هذه الإخفاقات ناتجة عن هجرة العلاقات، لكنها فجوة اختبارية ستُراجع في قسم الخادم والمصادقة بدلاً من إخفائها أو تعديل البيانات.

## قرار القسم

أصبح نموذج البيانات موثقاً بعلاقات Drizzle وقيود مرجعية فعلية، مع إبقاء معالجة تعدد الاشتراكات النشطة ضمن منطق الأعمال لا ضمن تعديل مباشر للسجلات. القسم التالي المقترح هو **تدقيق الخادم المشترك والمصادقة وواجهات API**، مع أولوية لفهم أسباب إخفاقات Vitest، والتحقق من حماية أدوار الإدارة، ومراجعة العقود بين API والواجهات.

**حالة القسم:** اكتمل تدقيق قاعدة البيانات وتطبيق إصلاح العلاقات دون تغييرات تدميرية.
